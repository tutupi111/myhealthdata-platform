# v0.4 AI 自动解析医疗资料 · 设置说明

v0.4 在患者上传文件后自动提取文本、调用 AI 做结构化解析，并写回 `health_records`。本阶段实现最小可用闭环，优先支持 PDF、DOCX；图片为占位，不要求高精度 OCR。

---

## 一、环境变量

除 v0.2 / v0.3 已有配置外，无需新增环境变量。AI 模型与任务路由使用 v0.3 后台配置：

- **Supabase**：`NEXT_PUBLIC_SUPABASE_URL`、`SUPABASE_SERVICE_ROLE_KEY`、`MOCK_PATIENT_ID`
- **AI 模型**：在管理后台「AI 模型」中配置，API Key 等写在 `ai_models` 表中
- **任务路由**：在「AI 任务」中为 `structured_extract` 选择 preferred 模型

若未配置 `structured_extract` 的 preferred 模型或未填写 `api_key`，上传 PDF/DOCX 后文本会正常提取，但 AI 解析会失败，记录将处于 `processing_status = failed`，错误信息写入 `processing_error`。

---

## 二、数据库迁移

在 Supabase SQL Editor 中执行：

**`docs/supabase-v0.4-health-records-ai-fields.sql`**

为 `health_records` 表新增列：

- `extracted_text`（text）
- `doc_type`（text）
- `ai_summary`（text）
- `structured_data`（jsonb）
- `tags`（text[]）
- `processing_error`（text）
- `updated_at`（timestamptz）

未执行迁移时，上传接口在写入解析结果时会报错，需先完成迁移。

---

## 三、如何配置模型

1. 登录管理后台，进入 **AI 模型**（/admin/ai-models），新增或编辑一个模型：
   - **Provider**：如 `openai`
   - **模型名称**：如 `gpt-4o` 或 `gpt-4o-mini`
   - **Base URL**：使用 OpenAI 官方可留空；自建或代理填完整地址，如 `https://your-proxy.com/v1`
   - **API Key**：必填，用于调用 Chat Completions
   - 勾选 **支持 JSON**（structured_extract 需要 JSON 输出）
   - **启用**、可选 **默认模型**

2. 进入 **AI 任务**（/admin/ai-tasks），找到「结构化抽取」一行，点击 **编辑**：
   - **首选模型**：选择上一步创建的模型
   - **备用模型**：可选
   - **超时** / **Max Tokens**：按需调整（默认 60s、4096）
   - **启用该任务**：勾选

保存后，下次上传 PDF/DOCX 将使用该模型进行解析。

---

## 四、当前支持的文件类型

| 类型 | 扩展名 | 文本提取 | AI 解析 |
|------|--------|----------|---------|
| PDF | .pdf | ✅ 使用 pdf-parse 提取正文 | ✅ 提取成功后调用 structured_extract |
| Word | .docx / .doc | ✅ 使用 mammoth 提取正文 | ✅ 同上 |
| 图片 | .jpg, .png | 占位，返回「图片暂未解析」 | 不调用 AI，直接写 doc_type=image_unparsed、ai_summary=「图片暂未解析」、status=completed |

图片上传后不会报错，但不会做真实 OCR；后续版本可在此处接入 OCR 再走同一套 AI 解析。

---

## 五、上传后处理流程

1. 用户选择文件，调用 `POST /api/upload`。
2. 服务端校验类型与大小，上传到 Supabase Storage，插入 `health_records`（`processing_status = uploaded`）。
3. **文本提取**：根据 MIME 类型对文件 buffer 做提取：
   - PDF → pdf-parse
   - DOCX/DOC → mammoth
   - 图片 → 占位文案
4. **分支**：
   - **图片或占位**：直接更新记录（`extracted_text`、`doc_type = image_unparsed`、`ai_summary`、`tags = []`、`structured_data = {}`、`processing_status = completed`）。
   - **PDF/DOCX**：调用 **structured_extract**（从 `ai_task_configs` 取 preferred 模型，从 `ai_models` 取 base_url、api_key、model_name），请求兼容 OpenAI 的 Chat Completions，要求返回 JSON。
5. **解析成功**：更新 `extracted_text`、`doc_type`、`ai_summary`、`structured_data`、`tags`、`processing_status = completed`、`processing_error = null`。
6. **解析失败**：更新 `extracted_text`（若有）、`processing_status = failed`、`processing_error` 为错误信息。
7. 接口返回当前记录（含上述新字段），前端可展示状态、摘要、标签与结构化数据。

所有步骤在同一请求内同步执行，上传响应时间会随文件大小与 AI 延迟增加。

---

## 六、解析输出结构

AI 返回的 JSON 需至少包含（英文 key）：

- **document_type**：如 `lab_report`、`discharge_summary`、`outpatient_note`、`image_unparsed`
- **summary**：简短中文摘要
- **tags**：字符串数组
- **structured_data**：对象，可含 `hospital`、`date`、`diagnosis`、`tests`、`notes` 等

示例见 PRD `docs/AI-Upload-Module-PRD-v1.md`。若模型返回格式不符或解析失败，会写入 `processing_error` 并将状态置为 `failed`。

---

## 七、前端展示

- **健康档案列表**（/patient/records）：展示 `processing_status`、`doc_type`、`ai_summary`（一行）、`tags`（标签）。
- **记录详情**（/patient/records/[id]）：展示处理状态、文档类型、AI 摘要、标签、结构化数据（键值 + JSON 区块）、处理错误（若失败）。

---

## 八、故障排查

- **上传成功但状态一直「已上传」**：检查是否执行了 v0.4 的 SQL 迁移；若已执行，查看接口或服务端日志是否有更新报错。
- **状态为「失败」**：在记录详情页查看 `processing_error`；常见原因：未配置 preferred 模型、api_key 未填或错误、模型不支持 JSON、网络/超时。
- **图片上传无解析**：符合当前设计，图片仅做占位并标记 `doc_type = image_unparsed`。
